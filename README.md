# Wordkeep

英単語の間隔反復（SRS）学習PWA。単体HTMLファイル（`index.html`）で動作します。v4.3.0からログインが必須で、単語はアカウント（Firestore）に自動同期され、端末側の localStorage はその手元のコピーとして動きます。

姉妹アプリだった `idiomkeep.html`（熟語版）は提供終了しました（履歴からは復元可能）。

## 機能

- 単語の追加・検索・編集・削除（重複追加は防止）
- フラッシュカード（暗記用、復習スケジュールには影響しません）
- 4択 / **スペル入力** クイズ。4択の誤答はスペル/意味が似たものを優先的に選出（レーベンシュタイン距離の重み付きサンプリング）
- 間隔反復スケジュール（正解で **1→2→4→7→12→21→35→60→90日後**に再出題、不正解で最初からやり直し）
  - v5.2.0で刻みを見直した。旧 `[1,3,5,7,14,20,30,60,90]` は倍率が 3.0→1.67→1.4→2.0→… で、**記憶が最も弱い最初の1歩で3倍に飛び、その後で縮む**という逆の形だった。新しい刻みは 2.0→2.0→1.75→1.71→… と滑らかに広がり、復習日が 1/3/7/14/26/47/82/142/232日 に乗る。総日数は230→232日でほぼ不変、配列長が同じなので既存の `box` はそのまま有効
- **苦手な単語（リーチ）の検出**: `wrong>=4` かつ `wrong/seen>=0.4` の両方を満たす語。片方だけでは足りない（50回見て4回間違えた語は苦手ではない）。リストのバッジ・絞り込み・専用の復習タブに加えて、**間違えた直後にメモ欄をその場に出す**のが本命。不正解で箱が最初に戻る仕様のため、放置すると永久に周回して意欲を削るのが元の問題。一時期「不正解でも1段階戻るだけ」に緩めたが、90日→60日では間隔が長すぎて学習にならないため元の厳しさに戻した
- **自由学習はつねにランダム**。ここはスケジュールが存在しないモードなので期限順に意味がなく、先頭から20語取ると数百語あっても毎回同じ顔ぶれになっていた。**上限を掛ける前に**並べ替えるのはこのモードだけ——変える必要があるのが順番ではなく「どれを選ぶか」だから
- **1回の問題数は目盛り付きスライダー**（5 / 10 / 20 / 全部）。詳細は「スライダーについて」
- **重複の警告は「どこにあるか」まで言う**（`wordOwner()`）。「すでにあります」だけでは真だが役に立たない——知りたいのは**どこか**で、それが無いと確認しに行くしかない。探す範囲は今表示している単語帳ではなく**持っているもの全部**（自分の単語帳・作った単語帳・**ダウンロード済みの**パッケージ）。未ダウンロードのパッケージは意図的に見に行かない：1打鍵ごとに通信が要るうえ、取っていないパッケージは「そこに持っている」場所ではない
- **出題順のシャッフル**（復習をはじめる画面、既定はオフ）。**この回についての選択**なので、設定ではなくこれから何を学習するかを見ている場所に置いてある。並べ替えは**1回の問題数と1日の上限を掛けたあと**に行う。先に混ぜると、今日どれを出すかという期限順の判断そのものをくじ引きに置き換えてしまうため
- **単語のマーク**（お気に入り♡／苦手マーク⚠）。**形と色の両方で**分けてある（♡は赤、⚠はオレンジ）——最初は星と⚠だったが、どちらも黄色で判別できなかった。⚠を琥珀にした案はアプリのゴールドと近く、マークではなく主要ボタンに見えたためオレンジに。**答えた直後の画面から付けられる**のが要点で、「これ苦手だな」と感じたその瞬間が一番正確。復習の設定に範囲として出る（1つも付いていなければ出ない）ほか、単語リストは絞り込みチップで一覧できる。既存の苦手検出は`wrong`の自動判定なので、**本人の主観で付けるこの軸とは別物**として両立する。パッケージの単語のマークは進捗と同じキーに保存するので、単語ファイルを取り直しても消えない
- 辞書API（dictionaryapi.dev）＋翻訳API（MyMemory）による単語検索（ログイン不要）。英英辞書の定義も対象言語に翻訳して表示
- 入力中にDatamuse API（無料・キー不要）でオートコンプリート候補を追加表示。
  辞書に見つからない語には「もしかして」でスペル修正候補（定義付き）を提案
- 多言語対応：日本語 / English / 中文 / Français / العربية / 한국어 / Русский（UI表示と訳の言語を設定で切替、アラビア語はRTL対応）
- 学習の記録画面（下部タブの「記録」、またはヘッダーの🔥バッジから）。現在／最長の連続日数、学習した日数、通算正答率のタイル、直近14日の復習数の棒グラフ、半年分（26週）のGitHub風コントリビューションカレンダー（4段階の濃淡・セルにツールチップ）。集計元は各単語の`hist`（クイズの解答のみ。フラッシュカードはSRSに影響しない設計のため含まない）で、自分の単語帳（`wordkeep.v2`）とパッケージ（`wordkeep.packages.v1`）の両方を合算。日付の集計は既存のSRSと同じローカル暦日基準。`hist`は1単語あたり50件までなので、極端に復習の多い単語は古い分が切り捨てられる
- 単語の発音再生に対応（Web Speech API／オフライン・APIキー不要）。リスト・単語帳の表裏・クイズ・検索結果の🔊ボタンで再生。設定 > 発音 で自動再生のオン／オフ、アクセント（米／英）、速さ（ふつう／ゆっくり）を選択可。クイズは「意味→単語」出題のときだけ再生を出さない（答えの読み上げになるため）。macOSはネタ音声（Albert等）が一覧の先頭に並び、`default`音声はOSのUI言語（日本語）になるため、標準音声名（Samantha/Daniel/Google US English等）を優先して選択。非対応ブラウザでは発音セクションごと非表示
- ライト／ダークテーマ対応（設定 > 表示）。「自動（端末の設定に追従）／ライト／ダーク」を選択でき、基本の紺＋ゴールドはそのままに白い面を落ち着いたダークグレーへ切替。全色をCSS変数化し`:root[data-theme="dark"]`で上書き。自動時は`prefers-color-scheme`に追従（フォーカス／可視化時に再判定するフォールバックあり）、`<meta name="theme-color">`も同期
- テーマ別の単語パッケージ：あらかじめ用意した配布デッキを、リスト/単語帳/復習の各画面上部の単語帳セレクターから切り替えて学習。パッケージごとにコンプリート率（%）を表示し、進捗は自分の単語帳（`wordkeep.v2`）とは別キー（`wordkeep.packages.v1`、パッケージID＋英単語で一意）で完全に分離管理。収録は「語学留学の英単語 Part1 / Part2 / Part3」（各50語）。タイトル・単語の意味とも対応7言語すべてに翻訳済みで、表示言語に合わせて自動切替。リスト検索は単語・意味（全7言語）に部分一致
- ホームのCTA（プッシュ通知が使えない構成のため、開いた瞬間に復習へ誘導する代替）。`todayState()`が状態を判定し、状態に応じて: 未着手×要復習（連続記録が途切れる旨を明示）／今日学習済み×残りあり／要復習なし×連続中（自由学習へ誘導）／今日完了。要復習も連続記録もない場合は表示しない。ブラウザのタブのタイトルにも残り語数を表示
- 画面構成：下部タブは **ホーム / 単語 / ＋ / 復習 / 記録**。設定とプロフィールはヘッダー右上のメニュー（三本線）から
  - **ホーム**が起点。連続日数・今日の復習数・学習済み語数を並べ、状態に応じた1つのCTA（今日の復習／自由学習／最初の単語を追加）と、単語帳・追加・単語リスト・記録への入口を置く
  - **リストと単語帳は「単語」タブに統合**した。単語帳（カード）は行き先ではなく学習モードなので、リスト上部の**「リスト／カード」切り替え**で行き来する（単独のボタンは装飾に見え、押した先も伝わらなかった）。カード側にも同じ切り替えを置いてあるので専用の戻るボタンは不要。タブは`TAB_FOR`で「単語」が点灯したままになる
  - タブは5枠が上限という前提で設計してある。**将来ランキング／リーグを入れるときに動かすのは「記録」**：ホームがダッシュボードである以上、連続日数と進捗はもともとホームに出ており、記録タブの中身は大部分が重複する。ヒートマップ等の詳細はホームから1タップで開ければ足りる
- 初回起動時のチュートリアル（お試し単語5つを自動追加）、アップデート後の「更新のお知らせ」、設定 > ヘルプ下に全リリースの更新履歴
- インストール可能なPWA（`manifest.json` ＋ `service-worker.js`）。Android/Chromeではブラウザからホーム画面追加（インストール）を促され、追加後はオフラインでも開けます。`icon-192.png` / `icon-512.png` は暫定プレースホルダ（濃紺角丸＋「W」）で、正方形のロゴが用意でき次第そのまま差し替え可能
- ダブルタップでのズームを無効化（`touch-action:manipulation`）
- JSONバックアップの書き出し・読み込み

## 使い方

`index.html` をそのまま開くか、GitHub Pages などで公開するだけで動作します。ビルド手順は不要です。

## スペル入力モードについて

意味を見て英単語をタイプし、**正しく打てた瞬間に正解**になる（答え合わせボタンなし）。4択と違い消去法が効かないので、正解が「覚えている」証拠として意味を持つ。

- **標準キーボードは使えない。** iOS/Androidは予測変換の候補バーを出し、スペルを問う問題ではその候補が答えそのものになる。確実に抑止する方法がないため、**自前のキーボードを載せるしかない**
- 配列はQWERTY、見た目と打鍵感はiOSのキーボードに寄せてある。反応は`click`ではなく`pointerdown`（指を離すまで待つと打鍵感が出ない）
- タップ音は**ノイズバッファを1度だけ生成して再利用**する。毎回 `createBuffer` すると低速端末で音が目に見えて遅れる。Backspaceだけ帯域を下げて「戻す」音にしてある
- **PCではキーボードを表示せず物理キーで入力**（`maxTouchPoints` と `pointer: coarse` で判定）。物理キーは常時受け付けるので、キーボード付きタブレットでも動く
- ヒントは3段階：**文字数 → 最初の1文字 → 「答えを見る」**。ヒント2で入る1文字はBackspaceで消せない（打った文字ではないため）
- **ヒント使用は減点なし、答えを見たら不正解**。文字数と1文字を知っても綴りを出すのは自力であり、ヒントを罰すると「ヒントを使わずに投げ出す」方に倒れるため
- この形式は意味→単語が前提なので、**出題の向き設定を上書きする**

## 復習の開始フローについて

復習タブは開いた瞬間に出題せず、**単語帳・出題形式・問題数を選ぶ設定画面**を挟む。

- 変えたいものが1箇所に揃い、**周回中は設問以外が画面から消える**。従来は単語帳バーとモードタブが毎問の上にあり、解いている最中にいじる誘いになっていた
- **ホームのCTAはこの画面を飛ばして即開始する**。アプリを開いて答え始めるまでを1タップに保つのがあのボタンの存在理由なので、そこに画面を挟まない
- 出題形式・問題数・出題の向きを周回中に変更した場合は、設定画面へ戻す（途中の設問だけ古い形式で残るのを防ぐ）

## スペル入力のキーボードについて

- **画面最下部に `position:fixed` で固定**し、左右いっぱいまで使う。以前は本文と一緒に流れていたため、打っている最中にキーボードごと動き、両脇に余白が残っていた
- 浮かせた分の高さは本文側に確保する。`--kb-h`（キー高 × 4段 + 間隔 + パネルの余白）をCSSで先に押さえ、レイアウト後に実測値で上書きする。**測定だけに頼ると、描画前に測った0pxで何も確保されない**
- 確保した余白は`#quizBody`のインラインstyleなので、**設問を描き直す側が毎回戻す**（`clearKeyboardSpace()`）。PC版のようにキーボードが出ない画面へ持ち越すと、下に281pxの空白が残る
- **下段は左右で釣り合わせる。** 「-」だけを横に置くとスペースが左に寄り、どの携帯のキーボードも親指に教えていない位置になる。右のキーは**意図的に反応しない**——押して何かが起きるべきキーではなく、対称であること自体が仕事
  - 最初`<span>`で置いたら**12px細かった**。ボタンにはUAの左右6pxパディングが付いていて、`flex-basis:0`でも下限として効く。**釣り合わせる相手と同じ要素**にしないと釣り合わない
- 配列は **シフトの位置に「'」、削除が右、最下段にスペースキー**。iOSの標準に寄せてある。`'`・`-`・スペースは以前「答えに含まれるときだけ」出していたが、**問題ごとにキーボードの形が変わる方が打ちにくい**ので常設にした
- ヒントはキーボードの上のボタンが担うため、キー側の`?`は置いていない
- キー面・背面パネル・機能キーの3色を変数化（`--kb-key` / `--kb-bg` / `--kb-fn`）し、ライトとダークで別々に指定している

## 復習をはじめる画面について

**形式がこの画面の主役**で、範囲・問題数・シャッフルは1行の要約に畳んである。

4つの形式は**入力×出力の表**になっている。カードが2×2なのは並びの都合ではなく、これがそのまま意味だから：

| | 選ぶ | 打つ |
|---|---|---|
| **文字から** | 4択 | スペル入力 |
| **音から** | リスニング | ディクテーション |

- **4段すべてが同格に見えたのが問題だった。** 押しに来たボタン1つより先に、毎回4つの判断が並んでいた——記入用紙になっていた
- カードは**2列**なので、3つでも4つでも同じ形に収まる
- **設定シートから「クイズのタイプ」は削除した。** 選ぶ場所が2か所あるうえ、そちらはリスニングを知らないままになる。シャッフルを設定から出したのと同じ理由で、これは**この回についての選択**
- 要約行は開いている中身を言い直すので、スライダーやチェックを動かしたときは**再描画せずに文字だけ差し替える**（再描画すると指の下でパネルが閉じる）

## リスニングについて

**音声を聞いて意味を4択で選ぶ。** 実装は4択の裏返しで、問いが綴りではなく音になっただけ——選択肢の作り方も採点も既存のまま使える。

- **単語を画面に出さない。** 出したら問いそのものが答えになる。代わりに大きな再生ボタンを置いてある（ここで人が要るのは「もう一度聞く」だけ）
- **答えた瞬間に綴りへ差し替える。** 問いのために隠していたものを終わってからも隠し続けるのは、ただの出し惜しみ
- **自動再生の設定に関わらず鳴らす。** ほかの画面では設定に従うのが正しいが、ここでは音が問題そのもの
- `speechSynthesis`が無いブラウザでは**カードごと出さない**。出しておいて黙って失敗するよりよい。設定が古いモードを指していたら4択に戻す

**ディクテーションは既存2モードの合成**——問いはリスニングの再生ボタン、答えはスペル入力のキーボード。分岐を2つ足しただけで、採点も「惜しい」判定もヒントもそのまま効く。

- **意味も読み仮名も出さない。** 読み仮名は発音そのものなので、出せば答えになる
- **聞き取れても書けない単語は、調べることもできない。** 表の中で唯一空いていたマスであり、実害がいちばん大きい穴でもあった

## スペル入力の答え合わせについて

**単語ごとの箱**で表示し、打ち終わって合っていればその単語がその場で緑になる。

- **入力の仕組みには触っていない。** 単語の区切りは純粋に描画の問題なので、バッファは1本のまま、スロットをグループにまとめているだけ
- **表示の経路は2つあるが、規則は1つ。** 長さを見せる場合（ヒント済み／与えられた文字あり）と、見せない場合とで描くものは違うが、**どちらも単語に区切り、単語は終わった瞬間に判定する**。違うのは「この先の空きマスを描くか」だけで、そこが長さを漏らす部分。v5.29.0では単語ごとの緑が**長さを見せる経路にしか入っておらず**、既定の状態（ヒント未使用）では一度も働いていなかった
- **きっかけは2つ、どちらもタイマーではない。** 答えの長さ**以上**なら即座に（本人が打ち切ったということ）、そして**1文字でも消したとき**。消すことは「違うと思った」瞬間そのものなので、間を推し量るより正確で、しかも**消す直前の語**——本人が尋ねている語——について答えられる
- **足りない文字は空きで示す**（`exa_ple`）。打った側に印を付ける文字が無いので、空きそのものが印になる。重なった文字（`acc`／`omm`）のどこに空きを置くかは**真に同点**なので、テストは特定の並びではなく成り立つべき性質を確かめている
- **外したときは「正解と〜文字違います」と、違う文字を赤で示す。** これがいちばん効く変更で、**それまで何も起きなかった**——`checkSpell()`は完全一致でしか発火しないため、`brint`と打った人は沈黙だけを受け取り、近いのか全然違うのかも分からなかった
- レーベンシュタインの**経路を残して**、typedのどの文字が原因か（置換か、余分な挿入か）を出す。足りない文字は typed 側に印を付けようがないので付けない
- **採点は変えていない。** スペル問題はもともと完全一致か「答えを見る」でしか確定しないので、これは黙っていた場所に情報を足しただけ。3文字を超えたら**何も言わない**——その距離での件数は励ましではなく点数なので、空いているマスに語らせる
- **スペースは自動で埋める。** `spellTypeable`の文字クラスに空白が入っていたためユーザーが打つ扱いになっていて、単語を箱に分けたら**スペース位置に打った文字がgapに飲まれて消えた**。スペースキーは残したまま無害にしてある（問題ごとにキーボードの形が変わる方が打ちにくいため）

## 答えた問題を見返すことについて

復習中に右へスワイプ（PCでは ← キー）すると、**1つ前の**問題を見返せます。読むだけで、採点はやり直せません。

- **戻れるのは1問だけ**。最初の実装は周回の頭まで遡れたうえ、1歩目が「いま答えたばかりの問題」に着地していたので、**「1つ戻る」が見た目2つ戻って**いた。そして人が知りたいのは「今の、なんて単語だっけ」で、それは常に直前の1問
- **採点済みの問題は、すべて同じ関数を通して描く**。答えた直後・戻って見ている時・戻ってから帰ってきた時が同じ状態になる。これは行数の節約ではなく**バグの再発防止**：`resumeQuiz()`が`renderQ()`を呼んでいたため、採点済みの現在問題が未回答として描き直され、**もう一度答えると二重採点**された。間違える→戻る→進む→正解、で不正解を取り消せてしまう状態だった。今は回答済みの問題から回答可能な状態へ戻る経路が存在しない
- 戻った先にも**単語の詳細・音声・マーク**を置いてある。聞き直す・自分のメモを読む、が戻る理由そのものなので

## リストの編集（削除・移動）について

入口は**ボタン1つ**（「リストを編集」）。編集の手段は今後も増えるし、リストの上に動詞が並ぶのは**以前フィルタのチップを外した理由そのもの**——ツールバーになる。

- **自分の単語のときだけ。** パッケージは取得し直す共有コンテンツなので「消して」も次に開けば戻るし、単語帳はラベルであって入れ物ではない
- 選択中は<b>行そのものがチェックボックス</b>になる。誤タップで開いたり1件消えたりしない
- 「すべて」は**画面に出ているものすべて**。検索中に見えていない単語まで選ぶのは罠
- **まとめて追加には「すべて選択」「すべて解除」がある。** チェックは勝手に外れることがある（辞書に無かった、すでに持っている）ので、「全部」に戻すのが50回のタップであってはいけない。1回の貼り付けの中で重複している行だけは全選択でも入らない——同じ語が2つ入るので
- **重複でチェックを外すのは「自分の単語」のときだけ。** v5.26.0で重複の検索範囲をパッケージまで広げた結果、**ダウンロード済みパッケージに入っている語まで外れる**ようになっていた。パッケージは取り直す共有コンテンツなので、そこにあることと自分の単語帳に持っていることは別。`wordOwner()`は`{name,mine}`を返し、パッケージは**名前を出すだけの注記**にしてある
- **移動は`deck`を書き換えるだけ**——単語帳は単語に付いたラベルなので。ただし`touchWord()`で刻印しないと、差分同期の基準時刻が「触っていない」と判断して**移動がその端末から出ない**。学習の記録は単語側にあるので、そのまま付いていく
- 移動先は**今いる単語帳を除いた**一覧＋その場で新規作成。**パッケージへは移せない**：こちらが貼り替えてよいラベルではないし、移すのではなく複製することになる

## 周回中の画面について

**下タブは周回のあいだずっと隠す**（`body.in-round`）。以前は採点した瞬間に戻ってきていて、**周回から出る導線が、いちばん単語に集中してほしい瞬間に現れていた**。打鍵側ではキーボードが覆っていたので、挙動も揃っていなかった。

**答え合わせ後の3ボタンは、キーボードがあった場所に固定する。** 最後に押したキーと次に押すものが同じ位置にあるので指が動かない。ただし固定するのは**キーボードが元々そこにあった場合だけ**——PCや4択では何も覆っていないので、下に貼り付くバーはバーのためのバーになる（`actionsPinned()`）。

**マークの2ボタンと3タイルはひとつの塊として固定する**（`.q-bottom`）。タイルだけを固定した最初の版では、マークは札の上端に取り残されて**画面1つぶんの隙間**ができ、押すには下ではなく上へスクロールする必要があった。

**アニメーションする要素の中に`position:fixed`を置かないこと。** transformの掛かった要素は<b>その子孫のfixedの基準になる</b>ので、スライド中だけキーボードが問題カード基準で配置され、ヘッダーの上に0.2秒現れてから正位置へ跳んだ。`.q-slide`は<b>問題カードだけ</b>を包み、キーボードと答え合わせ欄はその外に出す。

**問題の切り替わりは左へ抜けて右から入る。**「次の問題」の`>`と同じ向き。`renderQ()`を`nextQuestion()`で包み、退場を先に見せてから描き直す——新しい問題が上に現れるだけでは、退場が起きていることにならない。`prefers-reduced-motion`では動かさない。

## 答え合わせ後の3ボタンについて

判定が出るとキーボードを閉じ、**「単語の詳細」「単語を聞く」「次の問題」**の3タイルを出す（4択でも同じ）。

- 覚えたてのうちに**メモを読み返す・発音を聞く**のは「次へ」と同じくらい価値があるのに、従来は幅いっぱいの「次の問題」1つだけだった。音声は判定枠の中の小さなスピーカー記号で、当たり判定が小さかったので廃止した
- キーボードを下げる処理は`grade()`に置いてある。**呼び出し側に任せると、1経路でも漏れたときキーボードが判定を覆い隠す**

## 周回の中断について

進行バーの右の✕で、解いている途中でも設定画面へ戻れる。**成績・次回日程・連続日数は1問ごとに保存している**ので、途中で抜けても解いた分はそのまま残る。

## 単語パッケージの外部化について

アプリに載っているのは**カタログだけ**（1件およそ170バイト：id・7言語のタイトル・語数・版）。単語そのものは `packages/<id>.json` にあり、**その単語帳を最初に開いたときに取得**して端末に保存する。

- 全部内蔵していた頃は、**誰も開かないパッケージの単語まで全員が毎回ダウンロードしていた**。しかも1本増やすたびにgzipで約3.8KB増える——「パッケージをどんどん増やす」とは真逆の性質だった。今は1本あたり約170バイト
- **取得は単語帳の一覧でタップした時点で走る。**「ダウンロード」ボタンを別に置くと2手になるが、タップは元々「これを勉強したい」の意味なので分ける理由がない
- **進捗と単語データは別のキーに置く**（`wordkeep.packages.v1` / `wordkeep.pkgwords.v1`）。どちらも**単語そのものをキーにしている**ので、内容を更新しても学習の進みが消えない
- **進捗率はカタログの`count`に対して数える。** 進捗はクラウド同期するが単語データはしないので、**別端末で勉強したパッケージは、まだ取得していなくても正しい％で表示される**
- **版はカタログが持つ。** URLに`?v=`を付けて取得し、保存する版もカタログの値にする。ファイル側の宣言を信じると、JSONの中の版を上げ忘れたときに**毎回ダウンロードし直す無限ループ**になる
- 取得できなかったとき・オフラインのときは、その場でメッセージを出して一覧に留まる。CTXは動かさない
- 同じパッケージを連打しても取得は1回（`pkgFetching`が進行中のPromiseを共有する）
- localStorageは`wordkeep.v2`と共用で上限はおよそ5MB。1本およそ9KBなので**100本で約900KB**。それを超える規模にするならIndexedDBへ移す
### パッケージの追加・更新

現在5本（語学留学 Part1〜3・IT/テック・ワーホリ）。**`packages/<id>.json` が唯一の正。** カタログは生成物なので手で書かない。

```bash
node tests/build-packages.mjs
```

これだけで、新しいファイルはカタログに追加され、既存のものは版・語数・タイトルが同期される。人が触るのはJSONだけなので、2箇所がずれようがない。

- ファイル名と`id`は一致させる。`v`は**単語を変えたら上げる**（上げないと既に取得済みの端末に届かない）
- 検証するのは：JSONとして読めるか、`id`とファイル名、`v`が1以上の整数、タイトルが7言語、全単語が7言語、**同じ単語の重複**（進捗は単語をキーにしているので衝突する）
- **ファイルを消してもカタログからは自動で消さない。** 警告だけ出す——単語が端末に無くても進捗は残っている人がいるので、消すかどうかは人が決める
- pre-commitからは`--check`で走る（検証のみ・書き換えない）。**ステージ後にindex.htmlを書き換えると、検証したものと違うものがcommitされる**



## ファイルサイズについて

非圧縮494KB、GitHub Pagesのgzip配信で**実転送量は167KB**。**「圧縮後200KBを超えたら分割を再検討する」と決めていた線を実際に超えている。**

- 2026-08-19に測った「97KB」をそのまま放置しており、実際にはv5.6.0の時点で既に194KBだった。**目安を置いても測り直さなければ意味がない**
- 内訳の大半は単語パッケージ3本（150語）と、7言語×50バージョン分のリリースノート。タブアイコンのdata URIは11KB（WebP）
- **次に容量が増える変更の前に、パッケージの外部化かリリースノートの間引きを決める**

## たまった復習の見せ方について

スケジュールは何百語でも返してくる。**その数字を見せることが、人が辞める理由**——作業量ではなく数字のほうが問題で、しかもホーム・タイル・タブバッジの3箇所から同時に出ていた。

- 利用者に見せる数はすべて**今日の目標で頭打ち**にする（`todayTarget()`）。残りは`backlogCount()`として**1回だけ、静かに**文章で出す
- **隠しているわけではない。** 単語は依然として期限切れだし、予定も一切変えていない。「210語の借金がある」を「今日は20語やる」に言い換えているだけで、真の総数は記録画面にある
- **出題側も同じ上限で切る**（`pickWords`）。ここを切らないと「今日は20語」と言いながら210語walkさせることになる
- 既定は20。設定の「1日に出す上限」で 10/20/30/50/上限なし から選べる

## 連続記録のページについて

**アプリ名の横の炎**か、記録タブの「現在の連続」から開く。

- 節目は 7 / 30 / 50 / 100 / 150 / 200 / 250 / 300 / 350 / 365。`STREAK_MILESTONES`が唯一の定義で、GA送信もバッジ表示もそこを見る（以前は`[7,30,100,365]`が`updateStreak`にべた書きされ、画面には何も出ていなかった）
- **ストリークフリーズをやっと表示した。** 月1つ・最大2つ貯まり、1日の空白を自動で埋める仕組みは前からあったが、記録タブの隅に文字が1行あるだけで、持っていることに誰も気づけなかった
- カレンダーは月送りでき、未来の月へは進めない
- **`.stk-c`に`aspect-ratio:1`を使わないこと。** グリッドのトラック幅と項目の高さが互いを参照して発散し、287pxの中で1列120pxに解決された。高さは固定値で持つ
- **先頭の空白セルに`empty`という名前を使わないこと。** `.empty`はアプリの空状態ブロック（padding 60px）で、そのpaddingが漏れて1行目だけ120pxになった

## 単語帳の下段について

**「前」「次」とマークは1行にまとめる。** 押せるものどうしなので同じ行に置き、位置表示（1/119）はその下へ——2行に分けると60px、まとめれば16px。

- **マークが、その画面に来た目的そのものを押し出していた。** v5.29.0でカードにマークを足したとき、スマホでは「次」がタブバーの下に隠れ、**下までスクロールしないと次に進めなく**なっていた
- カードの高さも`min(320px,38vh)`にした。固定320pxが、短い画面で押し出していた本体

## 単語帳のキーボード操作について

**←→で前後、Enter（とスペース）で裏返し。** PCで単語帳を使うと、カードをクリック→次をクリック、とマウスに手を伸ばし続けることになる。

- **他の画面・シートが開いているとき・入力欄にフォーカスがあるときは拾わない。** このアプリにはスペル入力の物理キーボード処理も別にあるので、キーの取り合いにならないよう条件を絞ってある

## 開き直したときの画面について

**しばらく離れてから開き直すとホームに戻る**（30分、`RESUME_HOME_AFTER`）。

- 起動時の`go('v-home')`だけでは足りない。**インストール済みPWAは再起動されない**ので、iOSはページを生かしたまま前の画面を出す
- **毎回戻すのは間違い。** 単語を追加している途中に辞書アプリを10秒見て戻っただけで入力が消える。「別の訪問」と言える長さが経ってから
- **周回中とシートが開いているときは動かさない。** 途中の回を捨てさせないため、そして開いているシートの下で画面がすり替わらないため

## 画面の状態を保つことについて

- **ビューごとにスクロール位置を覚えて復元する**（`viewScroll`）。長いリストの途中で他のタブを覗いて戻ると先頭に飛ばされるのは、タブの切り替えではなく居場所の紛失
- 復元は`requestAnimationFrame`の後。描き直す前だと、まだそこまで伸びていない画面に対してスクロールすることになる
- **シートは背景タップとEscでも閉じる。** どれが閉じてよいかは維持する一覧ではなく、**そのシートが閉じる手段を持っているかどうか**で決める（`.sheet-x`があるか）。ゲートと初回のようこそ画面は意図的に閉じる手段を持たないので、そのまま閉じられない
- 閉じるときは**そのシート自身の×を呼ぶ**。通知の案内は「答えた」ことを記録し、単語帳の一覧は編集状態を戻すので、クラスを外すだけでは足りない
- 背景タップは`e.target===ov`のときだけ。シート内で始まったクリックもここまで上がってくるので、それを拾うと**ボタンを押すたびに閉じる**

## 設定画面の行レイアウトについて

**選択ボタン（`.seg`）やプルダウン（`select.sel`）を持つ行は、テキストを上・コントロールを下に積む**（`.set-row.stack`）。

横並びのままだと、コントロールが自分の最小幅を取り切って、残りが説明文に回る。**「1日に出す上限」は幅25px・高さ695pxになり、説明が1文字ずつ縦に並んだ。**同じ潰れ方が他に6行あった（テーマ・出題の向き・言語など）。

クラスは**起動時にJSで付ける**——判定は「この行は幅の広いコントロールを持つか」なので、DOMに聞けばマークアップと食い違いようがない。

## 画面の余白とアイコンについて

- **ヘッダーは黒板ではない。** 語数と今日の復習を並べていたが、どちらもホームのタイルと復習タブのバッジに同じものが出ている。二重に払っていた分をやめて**116px → 63px**（54%）
- **連続日数だけは残した。** ただし独立した行ではなく**ワードマークの横**に置いてあるので、高さは増えていない。これは「何もしないと壊れる」唯一の数字なので、どの画面にいても見えている価値がある
- **単語リストの絞り込みは撤去した。** 使われていなかったうえ、リストの上に2行を常時占めていた。検索は残っている。苦手な単語は復習の設定画面から出題できるので導線は消えていない
- アイコンは単色SVGで統一（一覧・カード・ホームの各カード・空状態・記録のタイル）。**絵文字はプラットフォームが描くので端末ごとに形が変わる**うえ、色を揃えられない
- 設定のカテゴリだけは絵文字のまま。6つ並んでいるので、1つだけ差し替えると逆に浮く

## 出題画面の収まりについて

意味は一語のこともあれば一文のこともある。固定サイズだと**長い問題文が入力欄とヒントを画面外に押し出し、周回の開始がスクロールから始まっていた**。

- `fitQuestion()` が問題文の長さから文字サイズを段階的に決め、`-webkit-line-clamp:3` で3行に抑える。**CJKは同じ文字数でも約2倍の幅**を取るので別の段を使う
- 下限は読める限界（17px）。それ以下にはしない——収めるために読めなくしたら本末転倒
- 答えのマス目は**実測した幅から計算**する。`(幅 - 隙間×(文字数-1)) ÷ 文字数` を 20〜34px に収める。表で決め打ちすると画面幅が変わったときに破綻する。20pxを下回るなら2行に折り返す
- **ヒントを押したら入力済みの文字を消す。** 文字数が判明した直後に書きかけの綴りが残っていると、正しい長さのマス目に間違った途中経過が乗って読みにくい（epopの挙動）

## アイコンについて

下タブ（ホーム・単語・復習・記録）とメニュー（プロフィール・フィードバック・設定）は、**単色シルエットのインラインSVG**。`fill:currentColor` なので、色はボタン側のCSSがそのまま決める。

- **選択中は`--tab-on`。** ダークは`--accent`（#f0b429）そのままだが、**ライトでは11pxのラベルが読めない**——白地に対して1.9:1しかない。ラベルだけ同系の濃い金（#a8730a・4.1:1）に落とし、アイコンは`--tab-on-ic`で明るい金のまま。2色だが同じ色相なので1色に見える
- 非選択は`--muted`。以前の`opacity`ではなく色で表現している
- **生成されたSVGは光学サイズが揃っていない。** 実測すると歯車は中心が3.2ズレて面積が35%小さく、復習は21%大きかった。パス自体は触らず、**各`viewBox`をずらして全部が枠の75.4%を占めるように正規化**してある。追加するときは`getBBox()`で同じ計算をすること
- **発音ボタンも同じ扱い。** 以前は🔊の絵文字で、プラットフォームが描くため端末ごとに形が違い、他のアイコンと揃わなかった。`SPEAKER_SVG`を「単語を聞く」タイルと共有している（別々に持つと片方だけ直して食い違う）
- 発音ボタンのサイズは**文脈で切り替える**。一覧では隣の文字に合わせて`em`、カードと出題では単独で置かれるので固定24px。`em`だけにすると16pxのラッパーを継いで、置き換える前の絵文字より小さくなった
- 以前はラスタ画像を使っており、色付きだったせいでライトテーマで消え、`drop-shadow`4枚重ねの縁取りで凌いでいた。**単色にしたことでその小細工ごと不要になった**（11KB → 1KB弱）。元の画像は`home.png`等として残っているが、もう参照していない

## スライダーについて

1回の問題数は、5 / 10 / 20 / 全部 の4か所で止まるスライダー。

- **`input[type=range]`ではなくポインタイベントで自前に動かしている。** これが要点で、**step付きのrangeはドラッグ中に目盛りへ飛ぶ**ため、つまみが指から遅れて段階的に追いつく。今は指に連続追従し、**離した時だけ**吸着する
- **吸着のトランジションはドラッグ中だけ切る。** 付けたままだと、つまみが「指のいる場所」ではなく「指のいた場所」へ寄っていくので、まさに重いと感じる動きになる
- **幾何はインデックスに対して置く。** 止まる場所は等間隔ではないし、「全部」はそもそも数値ではない
- **位置はピクセルではなく`calc()`の百分率。** 最初はJSで実測していたが、**閉じているシートの中で作られたスライダーは幅0を測る**のでつまみが左端に貼り付いた。ResizeObserverで直すより、レイアウトに任せて測定そのものを無くすほうが正しい。実測が必要なのは指が乗っている間だけで、そのときは必ず画面にある
- **1目盛りごとに画面を作り直さない。** 作り直すと、操作している要素そのものが消える。ドラッグは離した時に確定するので耐えるが、**矢印キーの長押しはフォーカスごと古いノードに置き去りになる**

## 効果音について

クイズの回答時に短い音を鳴らします（設定 → 効果音 でオフ可、既定はオン）。

- **音源ファイルを持たず Web Audio API で生成**している。単一HTML構成を崩さず、読み込みも増えず、初回からオフラインで鳴る
- 正解は上がる長三度（G5→C6）、不正解は低く短い2音。**ブザーにはしていない**：学習アプリで毎回不快な音が鳴るのは、学習をやめる理由になる
- オシレータは瞬間的にオン／オフすると可聴なクリックが出るため、短いアタック／ディケイのエンベロープをかけている
- ブラウザの自動再生ポリシーで `AudioContext` は操作があるまで suspended になる。回答クリック自体が操作なので、初回再生時に `resume()` する
- アプリ内キーボードの打鍵音は**2層**。帯域を絞ったノイズの破裂音がキーそのもので、その下に短い音程のある胴鳴り（三角波、文字410Hz／削除190Hz、45msで62%まで下降）を重ねる。**ノイズだけだと耳には砂嵐として届く**——正確なのに気持ちよくない、の正体がこれだった。1打ごとに音程を±3%だけ散らすので、長い単語を打っても機関銃にならない
- なお**iOSではWeb Audioがambientカテゴリで再生される**ため、本体のマナースイッチを切っていると打鍵音も効果音も鳴らない。ページ側からは変えられない
- 読み上げ（TTS）と重なると双方聞き取りにくいので、効果音がオンのときは発音を約340ms遅らせる。**先に「次の問題」を押した場合はタイマーを破棄する**（さもないと次の問題の上に前の単語が読み上げられる）

## 音量について

設定 → 音量 のスライダー1本が、**発音（TTS）と効果音の両方**に効きます。

- 2つは生成経路がまったく違う（生のオシレータ対プラットフォームの音声エンジン）ため、**それぞれに較正定数を持たせて初めて**1本のスライダーで一緒に動かせる。`TONE_LEVEL` / `TTS_LEVEL`
- 最初の実装は効果音のピーク振幅0.16に対しTTSの`volume`が未設定＝1.0で、**声のほうが圧倒的に大きかった**。音声はクレストファクタが高くRMSはピークの1/5程度、正弦波のRMSはピークの0.707なので、ピーク同士で合わせると合わない
- `OfflineAudioContext`で効果音を実際にレンダリングしてRMSを測り較正した。`TONE_LEVEL=0.62`で声の約4dB下（合図は内容の少し下にいるべき）、最大音量でもピーク0.68でクリップしない
- **プラットフォームのTTSの実出力はページから測定できない**ため、TTS側は一般的なクレストファクタからの推定。スライダーはこの不確かさを吸収する役目も持つ
- 不正解音は当初A3/F3（175〜220Hz）だったが、**スマホのスピーカーは300Hz以下をほとんど再生できない**ため、まさに本アプリが使われる端末で聞こえていなかった。G#4/D#4（311〜415Hz）へ移し、1kHz付近より感度が落ちる帯域なので少しだけ持ち上げている

## 単語詳細について

- **類義語**: 辞書API（dictionaryapi.dev）のレスポンスに品詞ごとの`synonyms`が含まれているため、それを保存・表示（最大6件、最大3品詞ぶん）。追加の通信は発生しない
- **品詞ラベル**: `POS_LABEL`で英語の生の品詞タグ（noun/verb/adjective等）を7言語の短い表記に変換してリストに常時表示
- **単語タップで詳細ポップアップ**: `wordDetailHTML(w)`をフラッシュカード裏面（`renderBack`）と共有し、内容が食い違わないようにしている
- **メモ欄（`note`）**: 単語追加時・リストの編集フォームの両方から自由記述できる（例文・覚え方など）。既存の単語オブジェクトに1フィールド足しただけなので、クラウド同期・検索・詳細ポップアップに自然に乗る。リストには📝アイコンで存在だけ示し、内容は詳細ポップアップで見る


## 多言語の導線について

- **対応外の言語のフォールバックは英語**。`navigatorLang()`は以前`'ja'`を返しており、**ドイツ語・スペイン語・タイ語などの端末は日本語UIで開いていた**。英語学習アプリである以上、どの利用者も英語には足がかりがある
- 初回起動は**言語選択が最初**（チュートリアルのstep 0）。ゲートもニックネーム入力もその後なので、選んだ言語で表示される
- **日本語混入の検出方法**: ひらがな（U+3040–309F）とカタカナ（U+30A0–30FF）は日本語にしか出現しない（中国語は漢字を共有するので漢字では判定できない）。日本語以外の6言語で全画面・全モーダルを走査し、これらの文字が出たら翻訳漏れとみなす
  - この走査で **「復習中に言語を変えると単語帳バーとモードタブが日本語のまま残る」** 不具合を発見した。周回中は`startQuiz()`を呼ばない設計のため再描画されていなかった
  - 中国語の文字列がカタカナ中黒（U+30FB）を使っていたのも同時に発見し、U+00B7 へ置換した

## ニックネームの審査について

ニックネームは v5.9.0 でランキングに載るようになった＝**全ログインユーザーに配信されるものに変わった**ので、内容チェックを入れた。それまでは文字数しか見ていなかった。

- **これはモデレーションではなく速度制限。** リストはアプリ内にあり、その気になれば自分のコピーから消せる。**本当の歯止めは管理ページの「改名」ボタン**（`admin.html`）で、7日クールダウンを無視して即座に変更し、同時にランキングの行を`delete`する
- 判定前に**大小文字・アクセント・全角・leet（`0→o` `3→e` `$→s`）・区切り文字**を畳む。`ｆ ｕ ｃ ｋ` も `n1gg3r` も同じ形になる
- **リストは2つに分けてある。** 部分一致（`NICK_BAN`）に入れていいのは、まともな語に含まれない語だけ。`dick` `cock` `shit` `ass` `rape` `しね` などは **Dickinson・Hancock・Shitake・Cassandra・Grape・しねま** に当たるので、完全一致（`NICK_BAN_WORD`）に置いた。**無実の人に「あなたの名前は不適切です」と言うほうが、1件見逃して管理者が直すより悪い**
- ゼロ幅文字とbidi制御文字も弾く。一覧では見えないうえ、bidiは行の他の文字を並べ替えられる
- `admin` `運営` `公式` などは「禁止」ではなく**予約**。なりすまし対策で、語そのものは無害だから完全一致のみ

## バックアップを残した理由

アカウントとクラウド同期がある今、手動のJSON書き出しは要らないのでは、という話が出た。**残す判断をした。**

- **クラウド同期はバックアップではない。** 削除も同期する。単語が消える不具合や誤操作が起きたら、その削除がtombstoneとして全端末とサーバーに伝わる。**同期の不具合が届かない場所にある唯一のコピーがこれ**
- Firebaseは無料枠の単一障害点。プロジェクトの停止・クォータ・ルールの事故で、全部が同時に消える
- **このリポジトリは実際に単語データを壊す不具合を出している**（`box`がNaNになる／`ownerUid`ガード／tombstoneの順序）。守る対象が仮定ではなく実績
- 維持費はほぼゼロ（設定に1行と30行程度のコード）

ただし**壊れていた**ので直した。`doExport()`は`DB`だけを書き出しており、**パッケージの進捗（`PKGDB`／別のlocalStorageキー）が入っていなかった**。復元すると成功したように見えてパッケージの学習分だけ消えていた。読み込み側はパッケージ単位でマージする（古いバックアップが新しいパッケージの進捗を消さないように）。

## 更新履歴の外部化について

**直近3バージョンだけを内蔵**し、それより前は`changelog.json`から「過去のバージョンを読み込む」で取得する。

- 49バージョン×7言語＝**gzip 60KB**を、ほぼ誰も開かないのに全員が毎回ダウンロードしていた。gzip 202KB → 152KB
- Service Workerは`changelog.json`を**プリキャッシュしない**（139KBを全員に配ることになる）。ただし一度取得したら保存するようにしたので、2回目以降はオフラインでも開けるし再取得もしない
- `clOlder`/`clLoading`は`let`ではなく`var`。`renderChangelog()`は起動時にこの行より前に呼ばれるので、`let`だとTDZで落ちる
- **URLに`?v=`でバージョンを付けている。** Service Workerは取得したものを保持するので、素の名前だと端末が最初に見たコピーで固定され、後から外部化したバージョンが永久に出てこない
- 内蔵は3件に保つ。リリースのたびに1件増えるので、`node tests/trim-changelog.mjs`で押し出す（このスクリプト自体に、削除文字数の一致・重要定義の残存・`node --check`の検証が入っている）

## アカウントの自分での削除について

プロフィール画面の一番下。**PINの再入力を必須**にしてある——Firebaseが古いセッションでの削除を拒むからでもあり、端末を持っている人が本人だという唯一の証明でもある。

- **順序は飾りではない。** Firestoreの文書は「まだ認証が通るうちに」全部消す。認証ユーザーを先に消すとルールが呼び出し元を認識しなくなり、**本人にも管理者にも二度と届かないデータが残る**
- 順序：再認証 → 単語（サブコレクションなので親を消しても消えない）→ board / push → 要約文書 → 認証ユーザー
- **端末側の掃除は`localStorage`を最初に消す。** ここで一度やらかしている：`navigator.serviceWorker.ready`はコントローラが無いとき**解決も拒否もしない**ので、先に`await`したらサーバー側は消えたのに端末には全単語が残った。`try/catch`は効かない——保留のPromiseは例外を投げない。Service Workerの後始末は2秒で打ち切る
- ルール変更は不要だった。本人による削除は既に許可されている

## エラー監視について

**Sentryではなく Firestore の`errors`コレクションに書く。** 管理ページの「エラー」タブで読む。

Sentryを選ばなかった理由：Firebaseは既に読み込んでいるので**新しく何かを信頼させる必要がない**、SDKの30KBを全員に配らずに済む、そして**利用者のデータが第三者に渡らない**。代わりに諦めているのはソースマップ・グルーピング・アラートで、これは「外で何か壊れたか」に答えるものであって、デバッガの代わりではない。

- **送るのは文言・スタック・発生箇所・バージョン・UA・言語・uidだけ。** 単語も学習記録も入らない
- **端末側で1セッション5件・1日20件に制限。** レンダリングのループの中で起きるエラーはループの速度で発火するので、上限が無いと**最初のそういうバグが数秒で1日分の書き込み枠を使い切り、同期ごと道連れにする**。アプリを壊す監視は無いほうがマシ
- 同じ文言・同じ行は**1回だけ**送る。重要なのは「起きた」ことで、何回繰り返したかではない
- ルール側にもサイズ上限を置く。クライアントの自己制限は制御ではない
- 管理ページでは同じ文言・行をまとめて「何種類 / 何人」で表示する。**1つのバグが20人に当たっているのは、直すもの1つであって20行ではない**
- 送信は`try/catch`で完全に握り潰す。**監視がページを壊す側になってはいけない**

## 通知について

**サーバーは中身のない「合図」だけを送り、文面は端末のService Workerが組み立てる。**

- そのため**送信側は誰がどの単語を持っているか一切知らない**。管理ページですら単語を読めない設計にしてあるので、通知のためにそこを崩したくなかった
- Service Workerは`localStorage`を読めないので、必要な最小限（連続日数・最終学習日・復習数・単語25件・文面の言語）を**IndexedDBにミラー**する。387バイト程度で、単語IDも次回日程も含まない
- **スロットは3つ**：習慣（普段の学習時刻の**30分前**、未学習のときだけ）／**夜20時（常に）**／**ラストコール22時**（今夜ほんとうに途切れるときだけ）
- **時刻を厳密に一致させてはいけない。** v5.27.0は`slots.includes(localHour)`で、その時のcronが飛べば**その日の通知が丸ごと消えた**。GitHubのスケジュールはbest-effortで、このリポジトリの実績でも**2時間超の欠落が4回、最大10.8時間**あった。いまは**「過ぎた中で一番遅いスロット」**を送り、送った印（`sentDay`/`sentMin`）で二重送信を防ぐ。飛んでも次の実行が拾う
- **夜のスロットは学習済みでも送る。** 「終わった日は1通も送らない」は正しく聞こえるが、**毎日きちんと続けている人には一度も届かない**ということでもあった。ストリークを一番よく守っている人が何も受け取らないのはおかしいので、そこはねぎらいの一言にしてある。結果、続いている人は**1日1通**、忘れている人は**最大3通**で緊急度が上がる
- **`sentDay`/`sentMin`はAdmin SDKが書くが、ルールの許可リストにも要る。** マージ書き込みでも`hasOnly()`は**結果のドキュメント**に対して評価されるので、載せ忘れるとクライアント側の書き込みが以後すべて弾かれる
- **ラストコールは今夜ほんとうに途切れる人にだけ。** 条件は「連続があり、かつ最後の学習が昨日」。それ以外に送ると、緊急な見た目の通知が何も緊急でない日に届き、緊急さそのものが効かなくなる
- **文面はスロット（＝配信時のローカル時刻）と状態で決まる。** プッシュにペイロードが無いので、Service Workerは**時計を見てどのスロットかを判断する**。送信側は習慣時刻・20時・22時にしか撃たないので、これで足りる
- **連続日数は上ではなく下に数える。** 「3日目です」は過去についての事実、「あと4日で習慣になります」はアプリを開く理由。節目の1〜2日前は「あと1日で7日連続です」に切り替わる——連続を持ったことがない人にとって、6日目は「続けよう」ではなく「あと1日で達成」
- **連続が切れたあとは自己ベストを出す。** 「7日」は6日やるまで他人の数字だが、自己ベストは**本人が到達したことのある**唯一の目標
- 連続が無ければ**単語の意味を聞く**（具体的に問われる方が、やることがあると告げられるより強い）。それも無ければ復習数、それも無ければ「まず1問だけ」
- **フリーズが残っている夜に「途切れます」は嘘。** フリーズは1日の欠けを埋めるので、その晩に連続は切れない。失われるのはフリーズ（月1つ・最大2つ）の方なので、そう書く。アプリが一度でも嘘をつくと、以後の通知は全部無価値になる
- **`streak.current`は次に解くまで更新されない。** 火曜に死んだ連続が金曜も12と読める。最終学習日から**生死を判定**しないと、持っていない連続を祝う通知が飛ぶ
- **夜20時と22時は同じtagを使い、後のものが前のものを置き換える。** 同じことを言う行が2つ並ばない。再通知（`renotify`）はラストコールだけに許す
- 送信は**GitHub Actionsの毎時cron**（`tools/send-reminders.mjs`）。購読ごとに希望する**ローカル時刻**を持たせ、スクリプト側で突き合わせるので**cronは1本で全タイムゾーンをカバーする**
- Firestoreの`push/{uid}`は**読み取り禁止**。送信はAdmin SDKでルールを迂回する。読めるようにすると、他人の購読エンドポイントを取得してそのブラウザに通知を送りつけられる
- 404/410が返った購読はその場で削除する（アンインストール・ストレージ削除・権限取り消し）。残すと永久に失敗し続ける
- **1通目は「その人が学習している時刻の30分前」に送る。** Duolingoは固定時刻ではなく**前日の学習から23.5時間後**に撃つので、毎日わずかに前倒しになり、習慣を追いかけるのではなく**習慣の前に立ち続ける**。cronが毎時なので、狙いをつけられる細かさはここまで。 固定時刻は毎日同じ時間に同じことを言うことになり、いちばん早く無視される。`lastActiveDate`から`studyMin`（ローカルの分）を出して購読に持たせ、同期のたびに更新する（習慣は動くので、先月の時刻に向けた通知はただの固定時刻に戻る）。2通目の夜は固定——役割が「その日の締め切り」なので相手ではなく時間に紐づく
- **サーバーに渡すのは4つだけ**：`studyMin`（いつ勉強するか）、`tzOffset`、`lastDay`（最後に学習したローカル暦日）、`hasStreak`（連続が**あるかどうか**の真偽のみ）。**連続の長さも単語も渡さない**
- **`lastDay`と`hasStreak`は v5.27.0 で足した。** 「今夜ほんとうに途切れる人にだけ送る」判断はサーバー側でしかできず、その判断がラストコールの価値のほぼ全部だから。整数1つと1ビットで、**常に真である通知と、3回に1回しか真でない通知**の差を買っている。ランキング参加者は`streak`も今日の回数もすでに公開のboardに出ているので、その人たちにとって新しい開示はゼロ
- **「何を勉強しているか」は依然として端末から出ない。** 出ているものは設定にそう書いてある
- **`say()`はテンプレートをそのまま返す。** 365日を超えて次の節目が無いとき、置換せずに本文へ渡していたので「あと{0}日で{1}日ストリークです」が**ロック画面に出る**ところだった。全分岐×3時刻で`{n}`が残らないことをテストしている
- **「Wordkeepを開く」という本文は消した。** アイコンと、OSが必ず出す送信元の表示が、同じことをすでに2回言っている。なお**その送信元表示（"from Wordkeep"）はアプリ側からは消せない**——プラットフォームがWeb Pushに必ず付けるもの
- **7日未満は損失回避を使わない。** 2日目の人に「連続が途切れます」と言っても失うものが無い。序盤は**習慣づくり**、積み上がってからは**失うこと**——同じ「やれ」でも効く理由が違う（`HABIT_UNTIL`）。許可を求める画面も同じで、「連続を守る」ではなく**「習慣をつくる」**と説明する方が許可率が上がる
- **「1問だけでいい」を通知にも許可画面にも書く。** 通知を見て「20分やらなきゃ」と思わせないための、いちばん安い一文
- **VAPID秘密鍵はGitHub Secretsにのみ置く。** リポジトリには公開鍵だけ
- **選択肢は1つだけ置く。** 「今はしない」を並べると、端末側の許可・拒否と合わせて二度断る機会を与えることになる。閉じる×は残す——1つの道を示すことと、閉じ込めることは違う
- **通知の案内は更新のお知らせの後に一度だけ。** ほとんどの人は設定を開かないので、設定に置くだけでは存在しないのと同じ。ただし**答えたら二度と聞かない**（`notifyAsked`）——繰り返し出る許可ダイアログは、断り方を教えるだけ
- 案内を出す条件は「実際に機能する状況」に限る：push対応・ログイン済み・OSがまだ拒否していない・単語が5語以上。**リマインドする中身が無い人に聞かない**
- **通知の文面は、作っている最中には誰にも見えない。** ロックされた画面に、何時間もあとに、再現するしかない状態から描かれる。だからここはアプリで最もテストが要る場所で、`tests/notify.test.mjs`（文面の選択）と`tests/slots.test.mjs`（送る／送らないの判断）がpre-commitで走る
- **トークンの自動取得はバックエンドを持たない限り不可能。** GitHubのトークン交換エンドポイントはCORSヘッダを返さないので、静的ページからOAuthを完了できない。そしてVAPID秘密鍵はGitHub Secretsにしか無いので、実際に送れるのはActionsだけ
- **トークンは要求するのではなく、作り方を書く。** 一度は設定に「届く通知を見てみる」を置いたが、これは**開発者の確認手段を利用者の設定画面に置いた**もので、普通の利用者には要らないものだった。消して、管理ページ側で手順を全部案内するようにしてある（URL・Repository access・PermissionsのActionsをRead and writeに、まで）。拒否されたときは**よくある原因**を出す——ほぼ権限の付け忘れであって、打ち間違いではない
- 管理ページの「通知テスト」は`workflow_dispatch`に`test_uid`を渡してActionsを1件だけ走らせる。**送信自体はGitHub側**で、秘密鍵はそこにしか無い。管理ページが使うGitHubトークンは**そのブラウザのlocalStorageにのみ**保存し、Firestoreには置かない

## 単語帳の共有について

**共有デッキは「作者がユーザーになったパッケージ」。** これが設計の全体で、同じ経路に乗せたので単語帳セレクター・リスト・カード・クイズ・コンプリート率・マーク・進捗の分離・「すでに〜にあります」の重複検出が**1行も書かずに動く**。違うのは2つだけ——単語の取得先（Firestore か `packages/*.json` か）と、カタログの行が端末側にあること。

- **配布はリンクのみ。ギャラリーも検索も作らない。** これは未完成ではなく制限で、**サーバーが無い以上どんな内容も事前審査ができない**。デッキは作者が送った相手にしか届かない形でしか安全に出せない。管理画面の「共有デッキ」タブが唯一の後ろ盾
- **受け取るにもログインが要る。** 一度は未ログインでも取り込める形にしたが、Wordkeepは**サインインして使うアプリ**で、そこだけ半端に使える状態になるほうが筋が悪い。転送されたリンクをidだけで拾われることも防げる
- **デッキのidはログインの往復をまたいで保持する**（`pendingDeck`）。ゲートは画面全体を差し替えるうえ、URLは開いた瞬間に掃除するので、そうしないとアカウントができた頃にはどのデッキだったか分からない
- **出ていくのは単語だけ。** box・次回日程・回数・履歴・マークは共有されない。メモは**公開時に選択**（既定では含めない）——語呂合わせなど、自分のために書いた私的なものが多いため
- **`sharedIdFor()` はidを返す。** レコードを返していたとき、2回目の公開でオブジェクトがドキュメントキーになり、**リンクを配った相手が持っているデッキとは別のデッキが黙って作られていた**
- **公開状態と取り込んだデッキは同期する**（`pubDecks` / `shared`）。進捗はもともと同期するので、これが無いとノートPCに「進捗はあるがデッキが無い」状態ができる。運ぶのはidと題名だけで、単語は端末ごとに取り直す（公式パッケージと同じ）
- **デッキごとのOGカードは作れない。** 静的な1ファイルなので、どのデッキのリンクも同じHTMLが返る。サーバーが無い以上デッキ別のmetaタグは描けないので、汎用のOGタグでカードだけ出し、**リンクに添えるメッセージ**（「〇〇さんが「句動詞」の単語帳を共有しました！」）が名前を伝える役を担う
- **共有デッキは1言語。** 公式パッケージは7言語持っているが、ユーザーの単語は自分の表示言語の意味しか持っていない。読む側が別言語なら、持っている方の言語にフォールバックする。**昇格させるときは翻訳が要る**

## ランキングについて

記録タブの上部で「わたしの記録」/「ランキング」を切り替える。**下タブは5枠が埋まっているので新設せず、性質の近い記録タブに同居させた。**

種目は5つ（今日の復習数・総復習数・単語数・連続日数・学習日数）。**順位は数字と色だけで表す**——1位＝ゴールド、2位＝シルバー、3位＝ブロンズ、以下は無彩色。絵文字は使っていない。

- データは Firestore の `board/{uid}`。**ニックネームと数値だけで、単語は一切入らない。** 読みは全ログインユーザー、書きは本人のみ（`firestore.rules`）
- **数値はクライアントが書くので、クライアント以上には信用できない。** ルールは型・範囲・フィールド名を縛って被害を限定するが、「本当にその回数やったか」は証明できない。厳密にやるなら単語履歴からサーバーが再計算する必要があり、それはCloud Functionの仕事
- **同点は同じ順位（1,2,2,4）にする。** 並び順のタイブレークにuidを使って安定させてある。これが無いとFirestoreが返した順のままになり、**同点の2人の順位が更新のたびに入れ替わって見えた**
- **「今日の復習数」は行が古いことがある。** 各行は持ち主が次にアプリを開くまで前日の数値のままなので、`todayIdx`が今日と一致する行だけを残している。2フィールドで絞る複合インデックスを避けるため、200件取ってから絞って上位50件を出す方式
- **種目タブは掲載人数の多い順に並び、既定もその先頭。** 宣言順では「今日の復習」が先頭で、そこは1〜2人しか載っていないことが多い。**名前が1つしかない板は、板が無いより悪い印象を与える**——ほかの4つは同じ時に埋まっているのに「誰もいない」と読める
- **人数を知るのに追加の読み取りは要らない。** どの種目も同じ`board`ドキュメント群への別のフィルタで、1件が5項目すべてを持っている。だから1回の取得から5種目ぶんを数えられるし、ついでに5種目ぶんのキャッシュも埋まる。**ただし取得件数が上限(200)未満のときだけ**——上限に張り付いていると、その種目の上位200人と別種目の上位200人は別の集団になりうる
- **自分でタブを選んだあとは並べ替えない。** 選んだものから人を動かすのは既定ではない
- **キャッシュは種目ごとに持つ。** 1つだけ持つ実装だと、チップを行き来するたびに再取得して**1回200ドキュメント読む**。無料枠は1日5万読み取りなので、これは実際に効く
- **遅い応答が現在の種目を上書きしないよう、`rankMetric`を再確認してから描画する。** 回線が遅いと、チップは「連続日数」なのに中身が「今日の復習」になっていた
- **同じ内容なら書き込まない。** 同期はどんな変更でも走るので、毎回同じ行を書くと書き込み枠を無駄にする
- **ニックネームを変えたら即座に反映する。** 次の同期まで古い名前が残っていた——不適切な名前を消したい人にとっては最悪の挙動
- **自分が50位圏外でも、順位は下に固定表示する。**「自分は何位なのか」が一番知りたいことなので、スクロールで探させない
- 参加は既定でオン、設定からいつでもオフ。**オフにした瞬間に行を`delete`する**（隠すだけでは、消してほしいと言った人が載ったままになる）
- 並べ替え・絞り込み・順位付けは`rankRows()`/`withRanks()`に切り出してテスト済み。公開する数値は`boardNum()`でNaN・負数・上限を潰す

## 単語帳の編集について

一覧の右の「✏️ 編集」から名前の変更と削除ができる。

- **削除しても単語は消えない。** 中身は「自分の単語帳」に移るだけで、確認ダイアログにも何語入っているかを出す。ラベルを消すつもりで語彙ごと消えるのは取り返しがつかない

- ボタンは枠と文字のあるチップにしてある。端に浮いた薄い16pxの絵文字は、コントロールではなく飾りとして読まれる

## クラウド同期（アカウント）について

**同期は差分。** 前回同期以降に変わった単語だけを読む。

- 以前は毎回`wcol.get()`で全件読み直しており、**コストが「語数 × 利用者数 × 同期回数」で増えていた**。実測で300語の利用者は1同期あたり301読み取り、無料枠の1日5万は**50人前後で尽きる**計算になる。しかも熱心に使う人ほど早く尽きるという逆向きの性質だった。差分にして**301 → 1読み取り**（変更なしの場合）
- **安全なのは`mergeCloud`が和集合だから。** 応答に無い単語は「変更なし」であって「削除された」ではない。削除はアカウント文書のtombstoneとして伝わり、そちらは毎回全部読む
- **`SYNC_SKEW`（6時間）ぶん余分に遡る。** `updatedAt`は書いた端末が刻むので、時計が遅れている端末の書き込みは他端末の基準時刻より過去に落ちて見逃される。6時間ぶん読み直すコストは数十件で、この種のバグを丸ごと消せる
- **送信側も差分にしないと逆に壊れる。** 応答に無い単語を「リモートに存在しない」と解釈すると、**毎回全語を再アップロード**することになる（`wordsToPush`）
- **削除はリモート応答で判定してはいけない。** 今日消した単語が数か月前に書かれていれば差分には現れず、削除が握り潰されて他端末から復活する。tombstone自身の時刻で判定する（`tombsToPush`）
- **基準時刻はアカウントごと。** 別アカウントでログインしたら必ず全件読む——前のアカウントの基準を使うと、見たことのないコレクションの差分を取って「完了」と判断してしまう
- 基準時刻は**同期の開始時刻**で、**commit成功後にのみ**進める。実行中に他端末が書いた変更が隙間に落ちないため、また失敗した送信が「済み」にならないため

## 管理ページ（`admin.html`）について

`https://yurihmhm.github.io/wordkeep/admin.html` で、フィードバックと登録ユーザーを一覧できます。管理者アカウントでログインが必要です。

- アクセス制御は**Firestoreのルールで担保**（`firestore.rules` にUIDを直書き）。ページのHTML自体は公開されているが、管理者以外はデータを1件も読めない。ページ側の `ADMIN_UID` は表示を出し分けるだけで、防御はサーバー側
- **フィードバック**: 本文・日時・ユーザー名（未ログインなら「未ログイン」）・バージョン・言語・単語数・UA。「対応済み」フラグと削除が可能
- **ユーザー**: ニックネーム・ログインID・単語数・連続日数・最長・最終同期。**単語の中身は読めない**（ルールで`users/{uid}`の要約ドキュメントのみ許可し、`words`サブコレクションには管理者権限を与えていない）
- **アカウントの削除は2手順**: Authentication（ログイン情報）とFirestore（学習データ）は別の場所にあるため、**Authenticationでユーザーを消しても管理ページの一覧からは消えない**。完全に消すには「Authentication → Users で削除」→「管理ページで データ削除」の2つが要る。先にAuthentication側を消すこと（ログインできる状態で学習データだけ消しても、次の同期で作り直される）
  - 管理ページの「データ削除」は、要約ドキュメントの `wordIds`（単語IDの配列）を使って単語ドキュメントをIDで削除してから要約を消す。**Firestoreは削除にread権限を要求しない**ため、管理者は単語を1件も読めないまま削除だけできる。`wordIds` を持たない古いドキュメント（v4.3.0以前に最後の同期をしたもの）は、そのアカウントが二度と同期しない限りIDを知る方法がないので、Firebaseコンソールから `words` コレクションを手動削除する
- **できないこと**: PINの閲覧（ハッシュ化のため原理的に不可）、PINの再設定。これらはFirebaseコンソールの Authentication → Users から行う
- `<meta name="robots" content="noindex, nofollow">` を指定

## データについて

単語データはブラウザの localStorage にのみ保存され、サーバーには送信されません（単語検索時に辞書・翻訳APIへ単語を送る場合を除く）。端末を変えたりブラウザデータを消すと失われるため、設定タブから定期的にバックアップ（JSON書き出し）することを推奨します。

消失対策として次の2つを入れています（`wordkeep.v2`の設定に保存）:

- **永続化の要求**: `navigator.storage.persist()` でブラウザの自動削除（iOS Safariは未インストールのサイトを約7日で削除）からの除外を要求。空の初回訪問では要求せず、単語が存在するときだけ・1セッション1回だけ要求します（Chromeはエンゲージメント基準で判定するため、データがある状態のほうが通りやすい）。状態は 設定 > データ > データの保護 で確認でき、手動で再要求も可能
- **手動のJSON書き出し／読み込み**: アカウント同期があるので必須ではないが、アプリ外に自分の控えを持つ手段として残している。読み込み時はストリークを上書きせず統合し、取り込んだ単語は即座にクラウドへ送る

## アクセス解析について

計測しているイベント: `app_open` / `page_view` / `word_lookup` / `word_added` / `word_deleted` / `home_cta_shown` / `home_cta_click` / `pronounce` / `tutorial_step` / `tutorial_done` / `quiz_started` / `quiz_completed` / `review_started` / `review_completed` / `streak_milestone` / `streak_freeze_used` / `package_opened` / `cloud_*` / `feedback_sent` / `nickname_set` / `storage_persist_result`

- **`word_lookup`**: 検索の成否を検索した時点で記録する。以前は`word_added`だけだったため、**失敗して諦めた検索が計測から丸ごと抜けていた**（成功率が実態より高く見える）
- **`home_cta_shown` / `home_cta_click`**: 表示と押下の両方を取るので押下率が出せる。`state`にどの状態のCTAだったか（要復習／連続記録の警告／自由学習／初回追加）を持たせてある
- **`pronounce`**: 🔊ボタンの操作のみ。自動再生を含めると、設定を触っていないだけで利用率が高く見えてしまう
- **`tutorial_step` / `tutorial_done`**: 離脱段階の計測。同じ段階は1回しか送らないので、戻る操作で後半の段階が水増しされない。`tutorial_done`は`skipped`と`last_step`を持つ
- 記録画面の閲覧は`page_view`（`/record`）で計測済みなので、そこからの継続率はGA側のコホートで出せる


Google Analytics 4（gtag.js）で匿名の利用状況（画面遷移、単語の追加・削除、復習・クイズの開始/完了と正答率など）を計測しています。`GA_MEASUREMENT_ID`（各ファイル冒頭の`G-XXXXXXXXXX`）を実際の測定IDに差し替えるまでは計測は動作しません。`localhost`/`127.0.0.1`/`file://`など開発環境では常に無効化されます。`app_name`パラメータで将来の別アプリと同一プロパティ内で横断比較できます。設定画面にも計測している旨を記載しています。

## AI機能について

以前は [Puter.js](https://puter.com) 経由でカタカナ→英単語のAI推測・例文生成を試みていましたが、Puter側の仕様で初回利用時にログインが必要になることが判明し、実用上使い物にならなかったため撤去しました。ログイン不要で使える無料AI APIが見つかれば再検討します。
